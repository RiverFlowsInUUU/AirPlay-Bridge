## 一、[严重-1] 重采样器历史缓冲塌缩 —— 确认，已修

### 我做了什么验证

我先用**真实的 `resampler.h` + MSVC** 编译了一个测试程序（而不是读代码判断），
复现了你的结论，并比你的 Python 移植多测了几个维度：

```
同一条输入（48000 → 44100，品质 100）：
  一口气喂完      44101 帧
  分 480 帧喂     44101 帧
  最大样点差      3582 / 32767  = 10.9%
  差异 >1000 的样点  70882 / 88202 = 80%
```

你的报告说「逐样点最大差异 3581」，我这里 3582（信号不同），
**结论一致**。

### 但我发现你的诊断描述的是现象，不是根因

你写的是「`histL_` 长度塌缩」。这没错，但我实测后发现**更根本的问题**：

```
修复前（原始代码，同一条输入）：
   分块      输出帧数   最大差异
     1        48000      52386     ← 连输出帧数都不对（多了 3900）
     2        45231      53904
     7        44470      54024
    64        44100        574     ← 几乎没事
   480        44101       3582
   882        44103      21002
  1024        44101      20541
  4096        44100        552     ← 几乎没事
```

**64 帧和 4096 帧几乎不出错，480 帧差 3582，1 帧差 52386 —— 完全没有规律。**

这正是"结构性缺陷"的特征：结果取决于**分块边界和插值窗口的相对位置**，
而不是单调地"分块越小越差"。所以：

- 你的判断（历史塌缩）是对的
- 但**只看 480 帧这一种分块，会得到"差异约 10%"的印象**；
  实际最坏情况是 1 帧分块下的 52386（满量程的 160%），而且连输出帧数都是错的
- 这也解释了为什么原有测试（一次性喂完 = 单块）测不出来 ——
  它恰好落在"几乎没事"的那一类里

根因在你的报告里没有点到：

```cpp
if (center + 1 >= total) break;          // 只检查前向边界
for (int k = -half; k <= half; ++k) {
    if (idx < 0 || idx >= total) continue;   // ← 左侧不足就跳过抽头
```

sinc 插值需要 `center ± half`（±33）个真实样点。**左侧不足时抽头被跳过，
归一化后的幅度和相位都是错的**，而「左侧不足」出现的频率随分块变小而升高。
历史缓冲塌缩只是让这个结构性缺陷更容易暴露。

### 修法：重写核心循环，不打补丁

我先试了两种"打补丁"的做法（都失败并已回退，过程记录在提交历史里）：

| 尝试 | 结果 |
|---|---|
| 改保留长度为 `taps_`，`pos_` 仍减 `consumed` | **更差**（52529，时间轴错位） |
| 改保留长度 + `pos_` 减 `newOrigin` | 480 帧对了（73），其他分块仍错 |

两次失败让我确认：**在原结构上改参数解决不了结构性问题。**

最终改成「连续输入历史 + 绝对读取位置」：

```cpp
// 维护:
//   histL_      从 histBaseAbs_ 这个绝对位置开始的输入片段
//   posAbs_     下一个输出样点在输入时间轴上的绝对位置
//
// 产出条件：posAbs_ 左右各有 taps_/2 个真实样点。
// 不足就等（下批数据到了再算），绝不跳过抽头。
if (leftNeed  <  histBaseAbs_) break;   // 左邻不够 → 等
if (rightNeed >  availEnd)     break;   // 右邻不够 → 等
```

**关键点：`reset()` 预填 `half` 个零代表"信号开始之前的静音"**，
这样第一个样点就有完整左邻，不需要跳过任何抽头。

（顺带修了一个我自己引入的 bug：`configure()` 里 `reset()` 排在 `taps_` 计算
**之前**，导致预填长度按 `half=0` 算 —— 修完后一个样点都产不出。
已在 `configure()` 末尾补第二次 `reset()`。）

### 验证结果

   1        44070         0
   2        44070         0
   7        44070         0
  64        44070         0

1024        44070         0

**任意分块，逐样点完全相同（差异 0，不是"小于 1 LSB"）。**

39.5 那组数据是在「一次性喂完」前提下测的，那个前提本身就掩盖了缺陷。

坦白说：修复后比原来的「最佳情况」还好 2.2 dB，这一点超出了我的预期，
也说明原实现即使在理想的单次调用下也不是最优。
