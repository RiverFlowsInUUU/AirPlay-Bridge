# 硬约束与禁止事项

**动手前必须读完这一份。** 违反任一条会导致构建失败、功能回归，
或重演一次已经踩过的坑。

每条的「为什么」在 [PITFALLS.md](PITFALLS.md)；某条看不懂时去那里找。
工作顺序见 [WORKFLOW.md](WORKFLOW.md)；架构见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 代码风格

**本仓库没有强制的风格配置**（没有 `.clang-format` / `.editorconfig` / `CONTRIBUTING.md`）。
以下是**现有代码的一致做法** —— 写新代码时跟随它，不要引入第二套：

| 项 | 现状 |
|---|---|
| 缩进 | 4 空格，不用 Tab |
| 头文件保护 | `#pragma once` |
| 注释语言 | **中文**（含代码注释与文档） |
| 文件头 | 部分文件有 SPDX 许可行 |
| 命名 | 函数小驼峰（`logLine` / `checkFirewallRule`）、类型大驼峰（`BridgeConfig` /`TrayIcon`）、常量 `k` 前缀（`kSilencePeak` / `kLatencyLevels`） |
| 字符串 | 源码是 UTF-8（靠 `/utf-8` 编译选项，见 C5）；界面文案走 i18n，见 [STYLE.md](STYLE.md) |
| 平台相关 | 一律用 Win32 API + `W` 后缀的宽字符版本（`LoadImageW` / `MessageBoxW`） |

**为什么不做成 `.clang-format`**：这个项目由 agent 维护、单线程迭代，
格式统一靠「跟随现有代码」就够了；引入一份配置文件反而多一处要同步的东西。
**如果哪天要引入，记得同时改这一节。**

## 硬约束

违反任一条会导致构建失败或功能回归。**原理与实测数据见
[docs/ARCHITECTURE.md](ARCHITECTURE.md) 和 [docs/DECISIONS.md](DECISIONS.md)。**

### C1 — 延迟只能通过 `latencyMs()` 设置

`latency_`（帧 @44.1kHz）在上游 `third_party/airplay2-sender-cpp/src/raop_sender.h`。补丁已把上游硬编码断言改为
按 `latencyMs()` 动态计算 —— **直接写死数值会让测试挂**。
**下限 250ms**：低于它接收端缓冲被掏空（underrun），听感就是爆音。

### C2 — 补丁是相对上游 `fc91350` 的 git diff

`patches/upstream-airplay2-sender-cpp.patch` 覆盖 4 个文件。重新生成：

```bash
cd third_party/airplay2-sender-cpp
git diff > ../../patches/upstream-airplay2-sender-cpp.patch
```

**重新生成后必须先 commit 再验证** —— `git clone` 只认已提交内容。

### C3 — 行尾必须是 LF

`.gitattributes` 已锁 `* text=auto eol=lf` 与 `*.patch -text`。补丁带 CRLF 时
`git apply` 会 reject。自检：`file patches/upstream-airplay2-sender-cpp.patch` ——
出现 `with CRLF line terminators` 即为异常。

### C4 — Mbed TLS 钉在 3.6.0

固定 commit `2ca6c285a0dd3f33982dd57299012dacab1ff206`。网络受限时用
`-DFETCHCONTENT_SOURCE_DIR_MBEDTLS=<目录>` 跳过下载（首次约 190MB）。

### C5 — MSVC 必须加 `/utf-8`

`add_compile_options(/utf-8)`，**必须对所有目标生效，包括上游目标**。
源码含中文注释，MSVC 默认按 GBK 解码，UTF-8 序列末字节恰好是 GBK 前导字节时
会吞掉换行，报「标识符未定义」这类诡异错误。

### C6 — WIN32 子系统下不能用 `__argc` / `__argv`

`WinMain` 中 `__argc` 恒为 0，参数被静默忽略。改用
`CommandLineToArgvW(GetCommandLineW(), &argc)`。

### C6b — 日志清理策略

`logLine()` 中两条规则任一满足就 `remove()` 重开：超过 30 天未写入，
或超过 512KB（挂机时每 2 秒一条心跳，不限制会涨到几十 MB）。

### C7 — 音质档位改的是采集侧重采样

在采集回调里先转到 44100，再 `setInputFormat(44100)` —— 引擎走 pass-through，
完全绕过它自己的重采样。**好处是不动第三方代码，补丁不用跟着更新。**

- 配置字段 `qualityLevel`（0–100）：`taps = 4 + 28 * q / 100`
- 老配置迁移：`quality`（0–3）→ `0→0, 1→30, 2→60, 3→100`。
  **不换算的话老的 3（=最好）会被当成 3%（=很差）**
- 档位名：快速(<10) / 标准(10–29) / 高(30–54) / 极高(55–79) / 至臻(≥80)
- 改档要重连；自测用 `resampler_test` 目标

### C8 — 无控制台程序的诊断输出要落盘

本项目是 WIN32 子系统，`AttachConsole(ATTACH_PARENT_PROCESS)` 在重定向场景下会失败。
诊断类输出必须同时写文件。参考实现：`src/device/audiodevices.h` 的 `audioOut()`。

### C9 — 进程必须声明 DPI 感知

`WinMain` 第一行调 `enableDpiAwareness()`，**必须在创建任何窗口之前**。
不声明的话，非 100% 缩放下 Windows 会把整个界面按比例位图放大，全部发虚。

### C10 — 排查「握手超时 / 一直连接中」时，先确认本程序有入站 UDP 放行规则

接收端会**主动** UDP 回连本机做时钟同步，这些是无主入站报文。没有放行规则时
它们被静默丢弃，接收端不回应 stream SETUP —— 日志停在 `RECORD 200 OK`，
10 秒后 `AirPlay handshake TIMEOUT`，界面永远是「连接中」。
**排查顺序：先看防火墙规则，再看协议。** 详见 [docs/DECISIONS.md](DECISIONS.md) D12。

### C11 — 流式 DSP 必须保证「分块不变性」

**同一条输入流，无论按多大的块喂进来，输出必须逐样点完全相同。**

线上 WASAPI 回调的帧数本来就不固定，所以这不是理论要求。重采样器曾经违反它：

```
修复前，同一条输入，仅分块大小不同：
  分块  1     最大样点差 52386  （满量程 32767 的 160%，且输出帧数都不对）
  分块 64     最大样点差   574
  分块 480    最大样点差  3582
  分块 4096   最大样点差   552
```

**结果取决于分块边界和插值窗口的相对位置，毫无规律可循。**

**要求：**
- 凡是有内部状态、被反复调用的 DSP 类（重采样、滤波、混音），
  必须有一个「不同分块大小 → 输出一致」的测试用例，
  且**差异必须严格为 0**，不是"小于几个 LSB"。
- 核心循环里**不允许出现「数据不够就跳过抽头」的写法** ——
  跳过会让幅度和相位随分块变化。数据不够时只能**等**。

**测试还必须覆盖被测对象的全部方向与量程，不能只测当前默认路径。**

只测「产品现在走的那条路」是不够的。踩过：分块不变性用例把采样率写死成
`48000 -> 44100`，于是上采样方向完全没被覆盖，而 `taps_` 为偶数时
`window_[k + half]` 会越界读 1 个元素 —— **恰好只在上采样时发生**。

**并且：不是所有缺陷都能用"分块不变性"查出来。**
越界读的是同一块堆内存，两种分块读到的内容恰好相同 → 逐样点对比显示"完全一致"，
但值本身是垃圾。**这类问题必须显式检查索引范围**
（例：断言 `2*(taps/2) <= window.size()-1`），而不是靠输出对比。

一句话：**不变量测试要针对缺陷的成因设计，不是只对比输出。**

详见 [docs/PITFALLS.md](PITFALLS.md) 的「分块不变性」。

### C12 — 低频触发 + 静默失败 = 按高频缺陷处理

判断一个 bug 要不要修，**不能只看触发频率**，还要看**触发时用户能不能察觉**。

| 组合 | 处理 |
|---|---|
| 高频 + 可见 | 必修（显然） |
| 高频 + 静默 | 必修（显然） |
| **低频 + 静默** | **按高频处理** —— 就是本条的规则 |
| 低频 + 可见 | 可排期（用户会遇到、也会报） |

**理由：低频但静默的失败，用户永远不知道自己遇上了。**
他不会报给我们，也就永远不会修 —— 一次 49.7 天才发生一次的
「设备搜索返回空」，在用户侧的表现是「今天音箱连不上」，
他不会想到是开机时间太久，我们也不会知道是他。

**本项目的三个实例**：
- `GetTickCount()` 32 位回绕 → 开机 49.7 天后设备搜索静默返回空（C12 起因）
- `audioOut` 的函数内静态 `FILE*` → 首次 `fopen` 失败后诊断日志永久消失
- 安装时 `--fix-firewall` 被单实例检测挡住 → 放行规则没配上，用户只看到「连不上」

**反例（可以排期）**：设备发现最坏 3.4 秒卡顿 —— 低频、但用户看得见（界面卡住），
会来报，所以我们知道。

### C13 — 改了 `third_party/` 必须同步 `patches/`

**本地编译用的是 `third_party/` 的工作区，CI 打出来的包用的是 `patches/`。**
两者不一致时，**我测的和用户装的不是同一份代码**。

2026-10-17 踩过：`latencyMin` 早在 v1.5.8 就从 `latency_/3` 改成了固定 11025，
但 `patches/upstream-airplay2-sender-cpp.patch` 一直没重新生成 ——
**十几个发布包里跑的都是那个早已废弃、我明确记录过「必然爆音」的 `/3` 值。**

**为什么一直没被发现**：`check-patch.yml` 只验证「补丁能 apply」，
旧补丁当然能 apply —— 它检查的是**有效**，不是**新鲜**。

**规矩**：
- 动 `third_party/` 里任何文件之后，**立刻**重新生成补丁：
  ```bash
  cd third_party/airplay2-sender-cpp && git diff > ../../patches/upstream-airplay2-sender-cpp.patch
  ```
- **验证方式不能是「CI 绿了」** —— 要在一份干净的 `git archive HEAD` 上
  `git apply` 一遍，再 grep 关键实现值，确认打出来的和你本地的一样。
- `check-patch.yml` 里有一份「标志性行」清单做防陈旧检查；
  **新增关键实现时同步更新那份清单**。

**判据一句话**：**你测的二进制和用户装的二进制，是不是同一份代码编出来的？**

**护栏的边界（要认清）**：

`check-patch.yml` 和 `release.yml` 里的「标志行」检查是**护栏，不是保险**。
CI 拿不到你本地未提交的改动 —— 清单永远可能落后于下一次真实改动，
所以它只能抓「补丁里少了已知的关键行」，抓不住「补丁里少了你刚加的那行」。

**两个 workflow 必须各自自检。** 2026-10-17 踩过：tag 推上去时
`检查上游补丁` 是 failure，而 `发布` job 照样 success ——
两个 workflow 相互独立，一个挂了不拦另一个。**现在已经把校验内置进
`release.yml` 的构建前置步骤**，让「tag → 包」这条路自己自洽。

**根治路径（如果 patch 机制反复出问题，就走这条）**：

把上游改动做成**真实的 fork 仓库提交**，用 submodule 直接指向 fork 的
commit —— 那样「改了没同步」这个类别的问题**在结构上消失**，
因为不再有「工作区 vs patch 文件」两份副本。
代价是要自己维护一个 fork（跟上游同步的活从 `git diff` 变成 `git merge`）。

现在没走这条路，是因为补丁只有 4 个文件、改动小，patch 机制更轻。
**但要知道这是备选，而不是「patch 机制天然可靠」。**
### C14 — 文档里「会变的事实」必须可检查，否则不写

文档会腐烂，不是因为没人勤奋，而是因为**写下的声明和实际之间没有连接**。

2026-10-18 审计出来的：`AGENTS.md` 写「有 19 条是踩过坑换来的」（实际 **32** 条）、
「硬约束 C1–C10」（实际到 **C13**）；`ARCHITECTURE.md` 写 `main()` 约 960 行
（实际 **1483** 行）。**这些数字全出现在「动手前必读」的位置。**

**为什么不做「每次改完全面排查文档」**：那种规则的触发条件太宽 ——
绝大多数改动（修一行逻辑、修个 bug）根本不动文档。**每次都触发、大部分时候没事可做的
规矩最终一定会被跳过**，而跳过第一次之后就没有第二次了。

所以分两层：

#### 第一层：能机械核对的，钉进 `tools/check_docs.py`

CI 每次 push 都跑（`.github/workflows/check-docs.yml`），
**`release.yml` 打包前也跑一次** —— 理由同 C13：两个 workflow 相互独立，
一个挂了不拦另一个。目前覆盖：

| 核对项 | 真值来源 |
|---|---|
| README 中英文的延迟档位 | `kLatencyLevels` |
| 延迟滑块范围 | `latency_dialog.cpp` 的 `spec.min/max` |
| 音量档位数量 | `kVolumeLevels` |
| 待机档位 | `kStandbyLevels` |
| 文档里的 `C1–Cn` | `RULES.md` 里的最大编号 |
| 文档里的「补丁覆盖 N 个文件」 | patch 里的 `diff --git` 数 |

**加了新的可核对声明，就同步在脚本里加一条断言。**

**找不到锚点会 FAIL，不是静默跳过** —— 否则「把声明删掉」会成为
悄悄关掉检查的手段。

#### 第二层：判断类的，走窄触发表（改了才查，不是每次查）

| 改了 | 要同步 |
|---|---|
| 加/删一条约束、给清单加项 | 引用它条数/编号的地方（编号已由脚本覆盖） |
| 档位 / 范围 / 默认值 | README 中英文档位表（已覆盖）+ 界面文案 |
| 用户能感知的行为 | README 的功能描述 + CHANGELOG |
| 构建 / 测试 / 发布流程 | `DEVELOPMENT.md` / `WORKFLOW.md` |
| 界面文案 / 文件名 | 全仓库 grep 旧名（见 STYLE.md） |
| `third_party/` 里任何文件 | `patches/`（C13） |

#### 写的时候

- **能不给数字就不给** —— 「每一条都是踩过坑换来的」比「有 19 条」耐放
- 必须给范围时给**编号区间**（`C1–C13`），它只在加条目时变、边界清楚

## 禁止事项

**都是实际踩过的，别重试。** 按主题分组，不是按发生时间。
**为什么有这些规则 → [docs/PITFALLS.md](PITFALLS.md)**（困惑时再读，不必通读）

### ① 状态与参数

- **改任何「状态字段」前，`grep -n "<字段>.store"` 列出所有写入点**，
  逐个确认配套动作（通知、清标志、更新 UI）。漏一处就会出现自相矛盾的行为，
  而且不报错不崩溃。踩过 **三次**（`standbyActive` / `wantReconnect` / `connected`）。
- **改结构体字段时，grep 它在同一函数内的所有赋值点** —— 后面的赋值会把你改的盖掉。
- **改「范围类参数」要覆盖四处**：档位表、默认值、**读取时的钳制**、UI 范围。
  最容易漏钳制 —— 表现为「菜单里选了，重启又变回去」。
- **静音待机的「0 秒」不能参与计时** —— 判据在 N=0 时恒成立，会连上就断、反复振荡。
  统一走 `standbyActiveConfig()`。
- **不要给引擎的类加成员变量** —— 试过两次，堆损坏崩溃。

### ② 路径与系统集成

- **往系统里存路径的功能都必须能自愈**：检查时比对实际路径；启动时发现指向的文件
  已不存在就自动修正。踩过 **两次**（防火墙规则、开机自启项）。
  但**「自动修正」有边界** —— 没这一项就不动、指向另一个存在的文件就不抢，见 PITFALLS。
- **一台机器上不允许两份副本并存** —— 规则按 exe 完整路径记录，两份会互相顶掉，
  永远修不好。**发布渠道只保留安装版。**
- **`netsh advfirewall firewall delete rule name="X"` 删的是全部同名规则** ——
  「只删多余那一条」这种设计从一开始就不成立。加规则前要**先全清**。
- **验证时污染了自己的环境，别把它当成产品缺陷** —— 我曾因此改掉一个原本正确的
  默认值，亲手制造了新的「两份并存」。默认值往往是有理由的。

### ③ 文案与行为

- **改提示文案不算修复 bug。** 说「已修复」之前必须确认改的是**行为**，
  不是**解释行为的文字**。判据：把用户的**操作路径**完整重跑一遍，**现象消失**才算修好。
  只改了文案 / 日志 / 措辞的，一律说「没修，只是让提示更清楚」。
- **同一个现象不许「解释」两次。** 用户第二次报同一问题时，先回看上次究竟动了什么。
- **用户报「X 不被认」，就去读判定 X 的那段代码。** 不要先改「提示」，
  也不要先改「产生 X 的流程」—— 判据错了，前面怎么改都不会对。
  （同一个现象被报了四次，前三次我都在改提示和安装流程。）

- **无人值守的启动路径不许创建可见 UI。**
  开机自启、安装程序调用、卸载清理 —— 这些场景**没人在看**，
  凭空弹出的窗口用户只能去关，而关掉它往往等于结束进程。
  判据是「**这次启动有没有人在看**」，不是「有没有参数」。
  （犯过：`argc > 1` 就 `AllocConsole`，导致开机自启弹黑框。见 [PITFALLS.md](PITFALLS.md)）

### ③b 音频与主循环

- **任何让主循环停摆的东西都会掐断声音** —— 模态窗口（`MessageBox` / `TrackPopupMenu` /
  自绘滑块窗）、同步扫描、长循环都算。RTP 是靠主循环里的 `pumpNonBlocking()` 喂的。
  加这类窗口时，**必须先确认「这期间谁在喂音频」**。
- **修「某一类模态窗口」时要列全** —— 同一个病踩过两次：v1.2.13 修了「打开菜单」，
  漏了「菜单回调里弹的窗」（v1.4.8 才补）。见 [PITFALLS.md](PITFALLS.md)。

### ④ 工具链与脚本

- **不要在生成的源码里写反斜杠转义** —— 会被吃掉或翻倍，**而且照样能编译**，
  只在运行时炸。踩过 **四次**。用 `const char QC = '"';` / `char(10)` /
  `static_cast<char>(0)` 代替。
- **批量替换要排除替换目标自身** —— 否则「所有 A 换成 B」会把 B 的定义也换掉，
  自己调自己 = 无限递归，**而且编译照样通过**。
- **Edit / 脚本改完，立刻 grep 复核。**
- **提交后核对 `git show --stat`，确认你要改的文件真的在里面。**
  改完被 `git checkout` / `git restore` 冲掉、而工具仍报「已替换 1 处」——
  **提交信息里写着改了 A 文件，`--stat` 里却没有 A**。
  这比「改了没生效」更隐蔽：它一路通过编译、通过冒烟、通过发版，
  直到用户试了说「没修好」才暴露。
  **判据**：提交前 `git show --stat HEAD -- <你改的文件>`，看不到就是没改。
- **同一个文件既读又写时，读和写绝不能出现在同一个表达式里** ——
  `open(f,'w').write(open(f).read())` 会先把文件截断成 0 字节。
- **`git add -A` 之前先 `git status`** —— 临时产物不进版本控制。
- **日志的最后一行不可靠**，不要用它推断崩溃点（日志有缓冲，崩溃时不会刷出来）。
  正确做法：在可疑点**前后各加一条打点**。
- **测试脚本跑完先确认「被测程序真的起来了、日志真的在写」**，再看结果。
- **看门狗报告里「最后阶段 + 有没有恢复」信息量极大**：有恢复 = 偶发卡顿；
  **没恢复 = 死锁**。

### ⑤ 对外表述

- **对外文案不要写 Apple TV** —— 设备列表默认屏蔽它（`hideAppleTV=true`），
  README、仓库 About、发布说明等所有对外描述只写「AirPlay 2 设备」。
- **示例里不许出现看起来像真实的设备名 / 局域网 IP**，用 `<设备名>` / `<设备 IP>`。
- **执行「以后不要 X」只作用于「以后」，不清理历史** —— 删除类操作尤其：
  动手前先问「我要删的这批里，有没有本来就不是 X 的东西」。
  （曾把 35 个历史 release 删空，不可恢复。）
- **不要在单元测试里依赖 `latency_` 的字面值** —— 见 C1。
- **原生菜单的限制**：不用 `enabled=false` 显示状态（整行会被变灰）；
  不用 emoji / 位图给菜单上色（不生效，只有系统勾选态能上色）；
  不做「点击才展开的独立菜单」（展开时主菜单会消失）。

### ⑥ 发布纪律

- **不许因为「只改了文档」就升版。**（用户明确要求写死）
  升版 = **给用户一个新安装包**。exe 和上一版一模一样时，**那个版本号是假的**。
  判据：这次改了 `src/` 下的代码吗？没改就**只 push**，CHANGELOG 也不记。
  （犯过：README 补了说明就照惯例发了版，用户一句话点破
  「代码没动 为啥升版呢？不是跟上版一致吗？」已撤回。）
- **发版前必须问自己：这次的 exe 和上一版有什么区别？答不上来就不发。**
  既有清单全在回答「这个版本好不好」，没有一项回答「该不该存在」。
- **发版前扫一眼最近的决定/待办** —— 指示落在对话里、不落到行动上就等于没听见。
