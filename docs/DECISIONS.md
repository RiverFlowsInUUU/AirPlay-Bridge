# 关键决策

面向 AI agent：为什么是这样。改代码前先读，避免推翻有理由的设计。
约束逐条在 [AGENTS.md](../AGENTS.md)，模块地图在 [ARCHITECTURE.md](ARCHITECTURE.md)。

## D1 — 用 AirPlay 2，而不是修 AirPlay 1

**背景**：TuneBlade（走 AirPlay 1 / RAOP）在 HomePod OS 27 上失效，
Airfoil、Roon 等一起哑火。Rogue Amoeba 确认为 Apple 侧改动（bug report #FB24452968）。

**决策**：接入走 AirPlay 2 的开源协议实现，不复刻 AirPlay 1。

**理由**：AirPlay 1 的握手路径已经是 Apple 单方面控制的历史包袱，闭源工具没有修复可能。
AirPlay 2 是当前协议，Apple 仍在维护。

**代价**：协议跟进依赖上游 `airplay2-sender-cpp` 继续维护。

## D2 — 设备发现用单播 mDNS

**决策**：先扫网段找 7000 端口开放的 IP，再对每个 IP 发**单播** mDNS 查询。

**理由**：Windows 上组播（224.0.0.251）经常被网卡或路由器拦掉，实测零应答。

**被否决**：直接用组播 mDNS —— 在目标机器上不可用。

**相关事实**：7000 端口开放是 HomePod 的 AirPlay 标志。

## D3 — 接管模式靠切默认播放设备，不写驱动

**决策**：连上设备时把系统默认播放设备切到虚拟声卡（CABLE Input），断开时切回。
使用未公开接口 `IPolicyConfig`。

**理由**：自写虚拟音频驱动需要处理驱动签名，且用户安装成本高。
配合现成的 [VB-Audio Virtual Cable](https://vb-audio.com/Cable/)，用户装一次即可。

**实现陷阱**：`sysvolume.cpp` 定义两个变体 ——

| 接口 | `ResetDeviceFormat` | CLSID | 适用 |
|---|---|---|---|
| `IPolicyConfig` | 有 | `{870af99c-...}` | 旧系统 |
| `IPolicyConfigVista` | 无 | `{294935CE-...}` | Win11（老 CLSID 未注册） |

**两个接口的 vtable 顺序不同**，混用会让 `SetDefaultEndpoint` 落到错误的槽位。
Vista 版还需 IID `{568b9108-44bf-b4-9006-86afe5b5a620}`。

**被否决**：自写虚拟驱动。

## D4 — 崩溃保护靠配置文件留标记

**决策**：切到虚拟声卡**之前**，把原设备名写进 `bridgeConfig.preCaptureDevice`。
启动时若该字段非空且当前默认是 CABLE，判定为上次异常退出，执行恢复。

**理由**：程序被强杀时没有机会执行清理，必须在启动侧兜底。

**关键约束**：**只有恢复成功才清标记**。失败必须保留标记，
否则用户会永久失去声音且程序不再尝试恢复。

## D5 — 重采样做在采集侧，不改协议引擎

**决策**：在采集回调里先把音频转到 44100，再 `setInputFormat(44100)`，
让引擎走 pass-through 分支。

**理由**：引擎自带两点线性插值，15kHz 以上信噪比塌到 6–14dB。
若直接改引擎源码，本地补丁要随上游每次变动重新适配。
做在采集侧**完全不动第三方代码，补丁不需要跟着更新**。

**代价**：必须自己实现并维护重采样器（`src/audio/resampler.h`）。
质量实测见 [ARCHITECTURE.md](ARCHITECTURE.md)。

**被否决**：改引擎的重采样实现。

## D6 — 采集默认单设备

**决策**：`CaptureMode::DefaultOnly`。多设备混音（`AllDevices`）实现保留但不启用。

**理由**：实测多台设备同时打开时采集全是静音，原因未查明（见 [AGENTS.md K2](../AGENTS.md)）。
接管模式下也不需要 —— 声音都进虚拟声卡了。

## D7 — 单文件 exe，静态链接 CRT

**决策**：产物是单个 `.exe`，静态链接 CRT，配置写在 `%LOCALAPPDATA%`。
不提供安装包。

> **已被 D15 修订** —— 现在只提供安装版。D7 关于「静态链接、
> 配置写 %LOCALAPPDATA%」的部分不变。

**理由**：用户下载即可运行，不需要装运行库，不需要处理安装/卸载。
代价是体积略大。

## D8 — 菜单状态用系统勾选态，不用颜色

**决策**：显示「已连接」用系统自带的勾选态（`checked=true`，显示为蓝色勾），
不使用 emoji 或自定义位图。

**理由**：Windows 原生菜单不支持 emoji 着色，`SetMenuItemBitmaps` 也不生效。
系统勾选态是唯一可靠的上色方式。

**相关约束**：用 `enabled=false` 显示状态会让整行变灰（连右侧数值一起灰掉），
因此不可选的行应做成「可点但空操作」。

## D9 — 可调项都做固定档 + 连续滑块

**决策**：延迟、音量、音质、静音待机都提供固定档位作为快捷入口，同时提供连续滑块（静音待机另有关闭项）。

**理由**：固定档位让用户快速落在一个合理值；滑块覆盖不同网络与设备组合的差异，
不必为每个场景预设档位。仅做固定档会让精细调节无从下手，
仅做滑块则没有推荐值。

## D10 — 菜单深色模式用 uxtheme 的未公开序号

**决策**：跟随系统深浅色主题。通过 uxtheme.dll 的未公开序号实现：
133 `AllowDarkModeForWindow`、135 `SetPreferredAppMode`、136 `FlushMenuThemes`。

**理由**：Win32 没有官方的菜单深色 API，Microsoft 自家的终端与记事本也走这条路。
深色模式下弹出一个白菜单过于突兀。

**代价**：序号可能随 Windows 版本变动。实现取不到序号时静默跳过，
菜单退回浅色，不会崩 —— 退化是外观层面，不影响功能。

**主题切换**：监听 `WM_SETTINGCHANGE` 的 `ImmersiveColorSet`，收到后重新应用并清菜单主题缓存。

**滑块窗口**：不走这条路，改为完全自绘 —— 见 D11。

## D11 — 调节窗口全自绘，不用系统控件

**决策**：延迟 / 音量 / 音质的调节窗口里没有任何子控件 —— 
没有 trackbar、没有 static、没有 button，全部用 GDI 自己画。

**理由**：系统控件的配色跟不上下面的两件事 ——
trackbar 根本没有深色主题，按钮也一直是浅灰的。
只把窗口背景刷成深色、控件还是浅色，比不改更难看。
而这窗口是三个调节项共用的门面，值得自己画。

**顺带解决的三件事**：

- 跟随系统深浅色（同一个窗口两套配色）
- 滑块主色取自托盘图标（#E05838），两处观感是一套
- 数值用大字号 + 档位评价用主色，一眼能读到当前状态

**实现要点**：双缓冲绘制；按 DPI 缩放所有尺寸；
标题栏用 `DWMWA_USE_IMMERSIVE_DARK_MODE` 跟随主题。

**代价**：这批绘制代码要自己维护，系统换皮不会自动跟上。
收益是可完全控制观感，且不必为深色模式依赖任何第三方控件库。

## D12 — 「一直连接中」是环境问题，程序只做检测 + 提示

**现象**：某台机器上装了程序后一直显示「连接中」，一次都没连上过。
日志停在 `RECORD 200 OK` 之后，stream SETUP 永远没有回应，10 秒后超时。

**根因**：Windows 防火墙没有给本程序留入站 UDP 白名单。
接收端会**主动**向发送端在 session SETUP 中声明的 `timingPort` / `controlPort`
发 UDP（NTP 式时钟同步）—— 这些是无主入站报文，没有白名单就被系统直接丢掉。
接收端收不到回话，拿不到时间基准，于是不回应 stream SETUP。

**证据**：放行入站规则后，同一份 exe、同一份配置 3/3 成功。
上游源码里早有这条提示 —— `third_party/airplay2-sender-cpp/src/raop_sender.cpp:490`
附近的注释写着「if the receiver never clock-syncs, check the Windows-Firewall
inbound rule for the app, these are unsolicited inbound UDP datagrams」，
上游 README 也有专门一节。我们此前缺这句话，导致排查时被误判成纯协议问题。

**结论**：**环境问题，不是代码问题**。程序无法自行修复，能做的只有两件事：

1. 连续握手失败 3 次后写一条可执行的日志提示（含动态取出的程序路径，
   及 `netsh advfirewall` 放行命令），只写一次，连接成功即复位。
   已存在本程序的入站放行规则时改为更轻的提示 —— 那种情况防火墙不是原因。
2. 托盘 tooltip 在同样条件下补一句「若持续失败请检查防火墙入站规则」。
   不弹气泡 —— 重连循环里弹气泡是骚扰。

**被否决**：程序**静默**自行添加防火墙规则。改防火墙是系统级操作，
必须让用户明确参与 —— 详见 D13。当时把「必须让用户参与」错当成了
「让用户自己去敲命令」，结果只在日志里给了一行 netsh。

## D13 — 放行规则：用户主动触发，程序负责维护

**背景**：D12 定的是「只检测、只提示」。实际用下来，「让用户自己去敲 netsh」
是开发者思维 —— 用户打开程序只想要它能用。

**决策**：把「改规则」做成菜单里的一项，程序负责检测、维护、去重：

| 时机 | 行为 |
|---|---|
| 启动时 | 检查放行规则是否指向**当前这个 exe**，不匹配就提示（不自己动手） |
| 用户点「修复连接问题」 | 提权加入站 UDP 规则（弹一次 UAC，用户同意才加） |
| 启动时发现规则指向已失效的文件 | 提示清理，用户同意后删掉 |

**规则按 exe 路径去重**：同名规则只留一条（优先保留不带序号的那条），
指向其它 exe 的全部删掉。规则绑定的是 exe 的**完整路径** ——
用户换目录、改名、删旧文件之后，旧规则会留下来指向一个不存在的文件；
而检查只看「有没有」不看「指向哪」时，就会出现「提示已配置好、实际没放行」。

**只碰名字以 `AirPlay Bridge inbound UDP` 开头的规则**，其它一律不动
（本机可能还有别的 AirPlay 工具留下的规则）。

**被否决**：静默自动添加（见 D12）；让用户自己敲命令（D12 的教训）。

## D14 — 首次运行引导只在手动启动时做

**决策**：首次运行的引导（问是否开机自启）只在用户**手动打开**时触发；
开机自启启动（带 `--last`）时绝不弹任何窗。引导标记 `askedAutoStart`
落盘，只做一次。

**理由**：自启启动发生在开机那一刻，用户多半不在电脑前 —— 弹窗会一直堆着；
而且每次开机被问一遍是骚扰。「首次运行一定是手动打开」这个前提是安全的：
程序不会自己给自己开自启。

**相关**：弹窗期间给看门狗打豁免。`MessageBox` 是模态的，主线程等用户作答
是预期行为、不是死锁；不豁免的话日志会被「主线程无响应」刷满，
真出问题时反而被淹掉。

## D15 — 增加安装版（修订 D7）

**背景**：D7 定的是「单文件 exe，不提供安装包」，理由是不用装运行库、不用处理
安装/卸载。但实际用下来暴露了这个选择的代价：**免安装版的 exe 位置不固定**。

而系统里有两样东西是**按 exe 完整路径**记录的：

| 东西 | 记在哪 |
|---|---|
| 开机自启项 | `HKCU\...\Run` 里写 `"<完整路径>" --last` |
| 防火墙放行规则 | `netsh` 的 `program=<完整路径>` |

用户每下载一个新版本（文件名带版本号）、或者换个目录、或者重命名，
这两样就全部失效。更麻烦的是：如果检查逻辑只看「有没有」、不看「指向哪」，
界面还会显示成「已配置好」，用户根本不知道它其实没生效。
**实测踩过两次** —— 防火墙规则失效一次、自启项失效一次。

**决策**：提供安装版，默认装到 `Program Files\AirPlayBridge\`，
**磁盘上的文件名固定为 `AirPlayBridge.exe`、不带版本号**。
以后升级装到同一个路径，那些系统集成继续有效，用户什么都不用管。

下载的包名仍然带版本号（`AirPlay-Bridge-Setup-vX.Y.Z.exe`）——
那只是下载时的临时文件，装完落到固定路径上就跟它无关了。
**免安装版已停止发布**（2026-10-16 起，只出安装版）。

原因不只是「两份都要维护更累」，而是**两份副本同时留在机器上会互相顶掉系统集成**：
防火墙放行规则按 exe 完整路径去重、只保留一条，所以谁点一次「修复连接问题」，
就把另一份的规则覆盖掉 —— 两份轮流提示「未被防火墙放行」，用户永远修不好。
（安装版的路径固定，不存在这个问题。）少一个分叉就少一类问题。

**代价**：安装那一下要管理员权限（一次性）；多一份安装脚本要维护；
CI 多一个产物。

**不冲突**：D7 的「静态链接 CRT、配置写 %LOCALAPPDATA%」依然成立 ——
安装版同样是单文件 exe，只是它待在一个固定的位置上。

**顺带**：卸载时会清理系统集成（防火墙规则 + 自启项），
不然程序删了之后它们会变成指向不存在文件的死记录。
