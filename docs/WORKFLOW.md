# 从零接手 · 工作流 · 交接

**这份文件回答：一个全新的 AI 拿到这个项目，怎么一步步开始干活，怎么收尾。**

规范细节在 [RULES.md](RULES.md)，操作命令在 [DEVELOPMENT.md](DEVELOPMENT.md)，
架构在 [ARCHITECTURE.md](ARCHITECTURE.md)。这里只讲**顺序和判断**。

---

## 一、冷启动（第一次进入项目）

### 第 0 步 — 读入口

读 [../AGENTS.md](../AGENTS.md)。它是目录，会告诉你每个问题去哪找答案。

### 第 1 步 — 搞清项目是什么

读 [ARCHITECTURE.md](ARCHITECTURE.md) 的「分层」「模块表」「数据流」。
**目的是知道：一个改动会落在哪一层。** 后面每次改代码前都要回来看这一份。

### 第 2 步 — 把环境跑起来

按 [DEVELOPMENT.md](DEVELOPMENT.md) 的「环境」「构建」走。

**这一步不通，后面什么都别谈。** 常见障碍：

| 症状 | 原因 |
|---|---|
| `git apply` 失败 | 补丁没打，或子模块没初始化（要 `--recursive`） |
| CMake 卡住很久 | 在拉 Mbed TLS（约 190MB），属正常；受限时用本地源目录 |
| 报「标识符未定义」 | `/utf-8` 没生效，见 RULES.md 的 C5 |
| 生成器找不到 | 别照抄文档里的生成器名，用 `cmake --help \| grep -i "visual studio"` |

### 第 3 步 — 环境自检（**最容易跳过，也最容易出事的一步**）

**验证你跑的是你刚编的那个二进制。** 三件事缺一不可：

1. **版本号** —— 产物里的版本和你以为的一致吗
2. **能起来** —— 程序真的在跑吗（进程在不在、日志文件有没有**新内容**）
3. **能连上** —— 托盘显示「已连接」，日志里没有异常输出

**为什么强调这一步**：历史上有两次「验证通过」，实际测的是**旧二进制**
（一次是安装被带到别处，一次是 `cd` 之后用了相对路径、程序压根没启动）。
版本不对，后面所有「通过」都是假的。

**日志**：`%LOCALAPPDATA%\AirPlayBridge\bridge.log`（**路径用资源管理器打开，
不要粘进终端** —— `%VAR%` 在 bash 里不展开）。

### 第 4 步 — 确认任务

在动手之前，能回答这几个问题才算确认了：

- **要改的是什么行为**（不是「要改哪句文案」）
- **落在哪一层**（采集 / 重采样 / 协议引擎 / 界面 / 安装）
- **涉及哪些相关点** —— 改状态字段就列全部写入点，改范围参数就列四处
  （见 [RULES.md](RULES.md) 的「状态与参数」）
- **有没有触到红线**（[RULES.md](RULES.md) 的禁止事项）
- **怎么验证** —— 说得出「改完之后看什么」才算确认了

**答不上来就别动手。** 至少先把「怎么验证」想清楚，否则改完无法判断对错。

### 第 5 步 — 读红线

**通读 [RULES.md](RULES.md) 的「禁止事项」那 19 条。** 都是踩过坑换来的，
每一条都对应过一次真实的用户投诉或数据损坏。读它花 5 分钟，比踩一次便宜。

某条看不懂「为什么这也不行」→ 去 [PITFALLS.md](PITFALLS.md) 找对应小节。

### 第 6 步 — 动手

见下面「二、改代码的节奏」。

## 二、改代码的节奏

### 先读，再改

1. **第三方库的问题，先读它的 README，再读源码里的注释。**
   搜 `TODO` / `FIXME` / `known issues` / `gotcha`。
   *（血泪：找了一整天的根因，就写在上游源码第 490 行的注释里 —— 我读了那个文件却没翻到。）*
2. **用户报「X 不被认」，就去读判定 X 的那段代码。**
   不要先改「提示」，也不要先改「产生 X 的流程」—— 判据错了，前面怎么改都不会对。
3. **用户报的现象和你复现的不一致时，先怀疑「路径不同」。**
   现象是用户描述的，**路径才是事实**。

### 小步改

- **一次一个逻辑改动**，改完立刻验证，别攒着
- **改完立刻 grep 复核那一行** —— 改动可能被后续操作冲掉，
  而编辑工具仍报告「已替换 1 处」
- **脚本改多个文件时，前面的成功不代表后面的也成功** ——
  跑完要看每个文件是否真的变了

### 验证

**编译通过 ≠ 可以提交，更 ≠ 可以发版。**

| 改动类型 | 至少要做的验证 |
|---|---|
| 任何代码 | 跑一次，看能不能连上 + 日志有无异常 |
| 界面文案 / 菜单 | **把最终文案打出来核对**（临时打点），不能只看「代码里包了函数」 |
| 状态 / 参数 | 改动的每个影响点都走一遍；**双向验证**（新行为对了 **且** 旧行为没被改坏） |
| 第三方库相关 | 跑上游测试 |
| 安装 / 发布 | 干净环境走一遍；**先核对产物版本号** |

两个关键判断：

- **反向验证**：只测「新行为生效」不够。如果实现变成「什么都不做」，
  很多单向测试照样通过。**要同时测「该保留的保留了」。**
- **包装正确 ≠ 显示正确** —— 中间还有取值、拼接、覆盖好几道手。
  UI 难截图时，用临时打点把最终值打出来核对，验完删掉并 `grep -c` 确认为 0。

## 三、提交

- **message 用中文**，格式 `前缀：一句话描述`
  （现有前缀：`修复` / `文档` / `纪律` / `清理` / `移除`）
- **补丁有改动时必须先 commit 再验证** —— `git clone` 只认已提交内容，见 C2
- 提交前 `git status` 看一眼，**别把自己的临时产物一起提交**
  （扫描输出、测试脚本、备份文件都不进版本控制）

**什么情况必须先 commit**：改了 `patches/` 下的补丁、或改了子模块里的内容。

## 四、交接

**半成品不能留在脑子里。** 收尾时逐条确认：

- [ ] 改代码 → 跑了验收（[DEVELOPMENT.md](DEVELOPMENT.md) 的「验收」）
- [ ] 改行为 → 同步了 [ARCHITECTURE.md](ARCHITECTURE.md) 或 [DECISIONS.md](DECISIONS.md)
- [ ] 改界面文案 → 全仓库 grep 过旧文案
- [ ] 有代码改动 → 更新了 [CHANGELOG.md](../CHANGELOG.md)（双语，中文在前）
- [ ] 验证 → **留下了证据**（日志片段 / 实测数据 / 命令输出），不是只说「通过了」
- [ ] 没做完 / 没解决的问题 → 写进 [../AGENTS.md](../AGENTS.md) 的
      「已知未解问题」或「挂账」
- [ ] 临时调试代码（`TEMP-` / `DIAG-` 打点、临时参数）→ **已删，并 `grep -c` 确认为 0**

**「留下了证据」这条特别重要** —— 下一个接手的人（包括换会话后的你自己）
只能看到代码和文档，看不到你的过程。**只写「验证通过」等于没写。**

## 五、一致性与交接（换模型 / 换 Agent / 换会话）

**目标是：换谁来、换几次会话，做的事都一样。**

### 靠什么保证

| 机制 | 说明 |
|---|---|
| **单一事实源** | 规范只在 [RULES.md](RULES.md) 和 [STYLE.md](STYLE.md) 各写一份，别处放指针。**副本一定会漂移。** |
| **AGENTS.md 是唯一入口** | 不建平台副本。新 Agent 无论什么工具，读同一份。 |
| **决策写进 [DECISIONS.md](DECISIONS.md)** | 不只写「选了什么」，还写「否决了什么、为什么」。否则下一个人会把否决过的方案再提一遍。 |
| **踩坑写进 [PITFALLS.md](PITFALLS.md)** | 禁令不带理由，下一个人遇到规则没覆盖的新情况就不知道该怎么办。 |
| **未解问题写进 AGENTS.md** | 半成品必须落到文件里，否则换会话就消失了。 |
| **验证要留证据** | 见上。 |

### 换 Agent 时的交接检查

1. 读 [../AGENTS.md](../AGENTS.md) → [RULES.md](RULES.md) → 本文
2. 读 [ARCHITECTURE.md](ARCHITECTURE.md)
3. 看 `git log --oneline -15` —— 最近在做什么
4. 看 [../AGENTS.md](../AGENTS.md) 的「已知未解问题」「挂账」—— 有没有半成品
5. 跑一次「环境自检」（本文第 3 步）
6. **不要假设上一个人的判断是对的** —— 尤其是「文档说它是这样」的时候，
   以**代码和可复现的实测**为准

### 三条最容易违反一致性的地方

- **改了一份 README 忘了另一份** —— 中英两份必须同步改
- **改了代码没改文档** —— 文档会变成「写着代码里没有的东西」，比没有更糟
- **只在对话里说了，没落到文件** —— 换会话即消失

## 六、什么情况必须停下来问人

**不要猜。** 遇到下面任何一条，标 `TODO(需人类确认)` 或直接问：

- **不确定某条规范该怎么理解**，而两种理解会导致不同实现
- **要动仓库之外的东西**（改 GitHub 仓库设置、删历史 release、改用户机器状态）
- **要动「已经发布出去」的东西** —— 删 release / 改 tag / force push
- **发现文档和代码矛盾**，且不知道哪边是对的
- **验证无法完成**（缺设备、缺权限、需要特定机器）
- **要引入新的依赖或新的外部服务**
- **需要判断「用户体验上哪个更好」** —— 这是产品决策，不是技术决策

**判断标准**：这个决定**做错了会不会伤害用户或不可恢复**？
会 → 停下来问。不会 → 做，并在提交里说清你的判断和依据。
