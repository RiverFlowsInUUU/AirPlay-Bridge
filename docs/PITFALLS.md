# 踩坑记录

**规则在 [AGENTS.md](../AGENTS.md) 的「禁止事项」，这里放**为什么**那条规则存在。**

AGENTS.md 里每条禁令只有一两行，新 agent 读完知道「不许做什么」就够了。
但**知道理由的人会做得更对** —— 尤其是当他遇到规则没覆盖到的新情况时。
这份文件就是那些理由。

**读法**：不用通读。AGENTS.md 里某条禁令让你困惑「为什么这也不行」时，
再来这里找对应的小节。

**例外**：**[⑧ 修完怎么自查](#-修完怎么自查)** 是唯一建议主动读的一节 ——
它不是某个 bug 的原因，是一套提交前该走的动作。
改过控制流（加守卫条件、挪动一段逻辑）之后照着过一遍，成本两分钟。

## ① 状态与参数

### 状态字段漏改 —— 同一个病犯过三次

改一个状态字段时，凡是「读这个字段就去自动做点什么」的地方都要一起看 ——
漏一处就会出现自相矛盾的行为，而且**不报错、不崩溃**。

| 字段 | 漏掉的地方 | 表现 |
|---|---|---|
| `standbyActive` | 残留未清 | 手动连接后自动重连永久失效 |
| `wantReconnect` | 残留未清 | 一次失败后永远连不上 |
| `connected` | 漏通知托盘 | 图标显示已连接、菜单显示未连接 |

`wantReconnect` 那次尤其难查：`start()` 不经过 `teardown()`，所以一旦某次失败
把它置起来，**本次进程内它一直是 true** —— 新会话建好约 5 秒后，退避循环看到
`running && wantReconnect` 成立，就**把一个健康的会话拆掉**，然后再连、再拆。
表现为「重启接收端也没用」，因为毒在程序自己的内存标志里。

**识别特征**：会话被拆但日志里**没有任何错误或超时** —— 拆它的是我们自己，不是对端。

### 结构体字段被后面的赋值覆盖

改 `notify()` 时给 `nid.dwInfoFlags` 设了 `NIIF_USER`（用我们自己的图标），
**但同一函数尾部另有一行 `nid.dwInfoFlags = NIIF_NONE;`** 把它盖回去了 ——
那才是「通知图标是灰的」的直接来源。

改一个字段时，**grep 它在同一函数内的所有赋值点**，不要只看你改的那一处。

### 范围类参数遗漏「钳制」

「延迟 / 音量 / 待机时长」这类范围参数，**至少存在于四个地方**：

1. 档位表（`kXxxLevels[]`）
2. 默认值（`config_store.h`）
3. **读取时的钳制**（`config_store.cpp`）
4. UI 的范围（滑块 `minValue` / `maxValue`）

最容易漏的是**第 3 个**。不改的话，菜单里选了 15 秒、重启又变回 10 秒 ——
而且不报错、不崩溃，很难查。

改之前先列：

```bash
grep -n "<字段名>" src/app/*.h src/app/*.cpp src/ui/*.cpp
sed -n '/kXxxLevels\[\]/,/};/p' src/app/airplay_bridge.cpp
```

### 「0 秒」不能参与计时

静音待机的判据是「现在 - 最后一次有声音的时刻 >= N 秒」。
**N 取 0 时这个条件恒成立** —— 连上就立刻断，然后在待机/唤醒之间反复振荡。

所以 0 在语义上就是「关闭」，判据统一走 `standbyActiveConfig()`
（要求开关打开**且**时长 > 0）。滑块拖到底、菜单里的「关闭」项，
两个入口共用这一个判据。

### 不要给引擎的类加成员变量

试过两次，导致堆损坏崩溃。加 `latencyMs_` 没事 —— 具体触发条件未查明，
但「事件通道重连」那个改动确实是加成员后崩的（见 AGENTS.md 的 K1）。

## ② 路径与系统集成

### 「存路径」型 bug —— 犯过两次

防火墙放行规则和开机自启项都属于这一类：

```
存了当时的 exe 路径 → 用户换目录或改名 → 键还在但指向不存在的文件
→ 而检查只看「有没有」、不看「指向哪」→ 菜单里照样打着勾，实际早就失效
```

开机自启那次：Windows 找不到 exe 时**静默跳过**（不报错、不提示），
用户只会觉得「怎么没自启」。

**修法**：① 检查时比对实际路径；② 启动时发现指向的文件已不存在就自动修正。

**但「自动修正」有边界**（实测过）:

| 情况 | 行为 |
|---|---|
| 没有这一项 | **什么都不做** —— 用户没开过（或主动关了），不该替他打开 |
| 指向另一个**存在**的文件 | **不抢** —— 那是另一个版本在用 |
| 指向的文件已不存在 | **自动修正** —— 明确是死路径，且用户当初开过 |

### 两份副本互相顶

放行规则和自启项都按 exe 的**完整路径**记录。机器上同时存在安装版和免安装版时，
两份路径不同 → 谁点一次「连接诊断」就把对方的规则顶掉 → 两份**轮流**提示
「尚未被放行」，**永远修不好**，而且真的连不上。

所以**发布渠道只保留安装版**。

### `netsh delete rule name="X"` 删的是全部同名规则

系统级工具通常按**名字**操作，做不到「只删其中一条」。

所以「加规则前先精确地只删多余那一条」这种设计**从一开始就不成立**。
实际后果链：

```
旧规则没删 → netsh add 加出第二条同名 → 后续「清理多余规则」按名字删
→ 两条一起消失 → 规则归零 → 连不上 + 每次启动都提示未放行
```

覆盖安装时最容易踩到（旧规则还在的时序窗口）。修法是加规则前**先全清**。

### 把自己造成的污染当成产品缺陷

我曾因为用 `/DIR=` 指向临时目录做验证，看到「装到别处」的现象，
就去改了一个**原本正确的默认行为**（`UsePreviousAppDir`），
结果亲手制造了新的「两份并存」。

**判断「某个默认行为是否有问题」之前先问**：我看到的现象，
在一个**干净环境**里也会发生吗？如果只在「我刚做过某个非常规操作」之后才出现，
**第一个嫌疑人是我自己，不是产品。**

**默认值往往是有理由的。** 改它之前必须能说清「原设计错在哪」，
而不是「我遇到的现象用默认值解释不了」—— 后者通常意味着我的观察方法有问题。

## ③ 文案与行为

### 「改提示文案」冒充修复 —— 同一个现象被报了四次

| 版本 | 我做了什么 | 为什么没用 |
|---|---|---|
| v1.2.52 | 把提示文案写详细了 | **没改行为** |
| v1.2.53 | 加了「检测到另一份副本」的提示 | **还是只改提示** |
| v1.2.55~58 | 改安装程序（那是另一个真问题） | **没碰到那个判据** |
| **v1.2.60** | **直接改判定规则的那段代码** | ✓ |

**共同点：我一直在「提示文案」和「安装流程」上打转，
从来没去读「判定哪条规则算陈旧」的那段代码。**

**规矩**：用户报「X 不被认」，就去读**判定 X 的那段代码**。
不要先改「提示」、也不要先改「产生 X 的流程」—— 判据错了，前面怎么改都不会对。

**「已修复」的判据**：把用户的**操作路径**完整重跑一遍，**现象消失**才算修好。
只改了文案 / 日志 / 措辞的，一律说「没修，只是让提示更清楚」。

### 「现象是用户描述的，路径才是事实」

用户报「连不上 + 每次提醒防火墙」，听起来像两个 bug。
实际是**一条链**：安装没装完整 → exe 是旧的、规则没配上 → 两个现象都出来。

**多个现象同时出现时，先问「它们有没有共同的上游」。**

复现不出用户的现象时，**先怀疑「用户走的路径和我不同」**，
而不是继续在同一个路径上挖代码。那次真根因是用户**在安装时旧版还在运行**，
而我一直用「卸载干净再装」的路径测。

## ④ 工具链与脚本

### 生成的源码里不要写反斜杠转义 —— 踩过四次

用脚本往 C++ 里插含引号/换行的代码时，反斜杠会被吃掉或翻倍。
**而且照样能编译**，只在运行时炸。

| 事故 | 现象 |
|---|---|
| 配置写入 | 整个 JSON 结构被带歪，`volume` 变成 63090400 |
| netsh 路径 | 变成 `C:\"/System32/netsh.exe` |
| 空字符 | `std::string out(n, '\0')` 里的 `\0` 被写成真空字节 |

**替代写法**：引号用 `const char QC = '"';`，换行用 `char(10)`，
空字符用 `static_cast<char>(0)`。Python 侧用 `chr(34)` / `chr(39)` 拼。

**另外**：涉及反斜杠的字符串比较，一律用 heredoc（`<< 'PYEOF'`）写脚本，
不要用 `python -c "..."` 加双引号 —— 转义层数会让人得到假象。

### 批量替换把自己也换了

把「所有 `MessageBoxW` 换成 `promptUser`」时，**`promptUser` 内部那句也被换了**
→ 自己调自己 = 无限递归。**而且编译照样通过**（语法完全合法），
只有运行时才会栈溢出崩掉。

**批量替换必须排除替换目标自身**，尤其「把所有 X 换成 Y」这种。

### 同一个文件既读又写

```python
io.open(f, 'w').write(io.open(f).read())    # ✗ 文件当场变 0 字节
```

`open(..., 'w')` **会先把文件截断**，然后再 `read()` 读到的是空的。
前面辛苦改的内容全没了。

```python
s = io.open(f, encoding='utf-8').read()     # ✓ 先读进变量
...改 s...
io.open(f, 'w', ..., newline=NL).write(s)   # 再写
```

**发现方式**：改完后 `grep` 一个明明存在的字符串、**返回 0** ——
这个信号（「刚改的东西 grep 不到」）要当成**「文件可能被毁了」的第一反应**，
不要当成「正则写错了」。

### 日志的最后一行不可靠

`logLine` 有缓冲，进程崩溃时**缓冲区里的内容不会刷出来**。
最后打出来那行只是「已经进了缓冲区」，不代表执行到了那里。

实测：按「日志停在 X」推断崩溃位置，**方向完全错了**。

**正确做法**：在可疑点的**前后各加一条打点**，能打出来的才是真的走到了。

### 「结果全是 0」先怀疑测试环境

两次「结果全是 0」其实是程序根本没启动（`cd` 到别处后用了相对路径）。
还有一次是 COM 没初始化（测试参数写在了 `CoInitializeEx` 之前）。

**看结果之前先看「有没有产生新日志」。**

**测试工具本身不可靠时，先怀疑工具，再怀疑被测对象。**
（曾因为 `SoundPlayer` 播的声音采不到，差点得出「采集链路坏了」的错误结论 ——
换成 `MediaPlayer` 立刻正常。）

**验证「某条分支」时，先确认进入该分支的前置条件成立** ——
不然会得出「改了没生效」的错误结论。

### 看门狗报告怎么读

「**最后阶段 + 有没有恢复**」这两个信息量极大：

- 有恢复 = 偶发卡顿，能忍
- **没恢复 = 死锁，致命**

`主线程无响应 257.6 秒，最后阶段: 空闲` ——「空闲」+ 永不恢复，
直接把范围缩到「不在扫描/握手/菜单（那些都有打点）」，一次定位到 `producer.join()`。

### 音频靠主循环推 —— 任何模态窗口都会掐断它

**症状**：点托盘菜单里的「关于」，声音丢一下。

**链路**：RTP 是靠 `pumpNonBlocking()` 喂给接收端的，而它是**主循环**在调。
任何跑自己消息循环的窗口（`TrackPopupMenu` / `MessageBox` / 自绘滑块窗口）
都会让主循环停摆 —— 没人推音频，接收端饿死，声音断。

**这个坑踩过两次，是同一个病：**

| 版本 | 现象 | 当时的修法 | 漏在哪 |
|---|---|---|---|
| v1.2.13 | **打开菜单**就丢声音 | 菜单打开期间挂一个 `WM_TIMER` 心跳，里面调 `pumpNonBlocking()` | 只覆盖了「菜单打开期间」 |
| v1.4.8 | **点菜单里的「关于」**丢声音 | 把 `KillTimer` 挪到菜单回调**之后** | — |

`showMenu()` 原本的时序：

```cpp
SetTimer(菜单心跳)      ← 菜单开着时靠它推音频
TrackPopupMenu(...)     ← 模态循环；心跳在跑，声音正常
KillTimer(菜单心跳)     ← ★ 这里就停了
cb(cmd)                 ← ★ 回调才执行，心跳已经没了
```

而「关于」的版本窗、连接诊断的确认框、四个滑块窗口，**全是在回调里同步弹出的**。

**为什么挪 `KillTimer` 就够了**：模态窗口的消息循环会把 `WM_TIMER` **派发到宿主窗口**，
所以只要定时器还在，心跳回调照常执行。

**这个前提实测过**（当时不确定 Win32 的行为，写了个独立探针）：

```
50ms 定时器 + MessageBox 弹窗 2.5 秒
BEFORE=4  AFTER=44  DELTA=40      ← 40 次约等于 2500/50，完全吻合
VERDICT=TIMER-ALIVE-IN-MODAL
```

**顺带修的防退化**：看门狗原本在弹窗期间**无条件豁免**
（`if (g_inUserPrompt) { stalled = false; continue; }`）——
万一将来心跳又没跑，声音会丢而日志一片安静。
现在弹窗期间单独盯心跳，停了就报「弹窗期间音频心跳停了 N 秒」。

**通用教训**：

> **「后台在喂数据」的功能，任何会让主循环停摆的东西都是它的敌人。**
> 模态窗口、同步等待、长循环 —— 都要问一句「这期间谁在喂」。
> 而修「某一类模态窗口」时，**要把所有让主循环停摆的入口列出来**，
> 否则就是打地鼠：修了菜单、漏了弹窗。

### 我们自己弹的提示音会混进转发的音频流

连接成功时会弹一个托盘气泡（「已连接: <设备名>」）。**Windows 默认会给它播系统提示音**，
除非在 `dwInfoFlags` 里带上 `NIIF_NOSOUND`。

而提示音的播放设备是**默认设备** —— 我们在「连上」这一刻刚好把默认设备切成了
CABLE Input（没有物理输出）。于是这个提示音：

- 本机听不见（CABLE 没有物理输出）
- 却被我们自己的采集录了进去
- 当作新会话的**第一段音频**送给音箱

用户听到的就是「刚连上有一声通知音，而且常常是爆的」。**10 次里有 6-7 次** ——
提示音落在开局窗口的哪个位置，每次都不同。

**本质：我们自己的界面提示音污染了我们正在转发的音频流。**

排查时先逐项量了六个候选（源数据削波 / 静音接缝 / 同步间隔 / 协议步骤 /
重采样相位 / 本地缓冲），**全部干净** —— 于是方向锁定在下游，最后落到自己的提示音上。

**规矩**：**凡是接管了用户默认设备的程序，它自己的任何提示音都会进入它转发的流。**
要么静音，要么让它在不被采集的设备上播放。

**顺带**：确认「源数据干不干净」最直接的办法是**把真正发出去的原始 PCM dump 下来**，
算削波数、相邻样点最大跳变、逐块峰值轮廓 —— 比读代码推、比看统计值都直接。

## ⑤ 对外表述

### 默认屏蔽了的东西，对外文案不能提

设备列表默认屏蔽 Apple TV（只显示 HomePod），但 README 首句和仓库 About
仍写着「HomePod / Apple TV」—— 与实际行为不符。
**凡是「默认屏蔽了 X」，对外文案就不能提 X。**

### 示例里不许有像真的设备名 / IP

公开仓库的示例（README 菜单示意图等）里出现真实设备名或局域网 IP 会被视为隐私泄露。
一律用 `<设备名>` / `<设备 IP>` 这种一眼假的写法。

**仓库 About、README、发布说明都算「对外文案」，最后一并扫一遍。**

### 「以后不要 X」不清理历史

执行这类指示时**只作用于「以后」**。删除类操作尤其 ——
动手前先问「我要删的这批里，有没有本来就不是 X 的东西」。

**事故**：清理历史 release 的免安装版时，把 v1.2.14~v1.2.48 共 **35 个**
只挂着裸 exe 的 release 一起删空了，GitHub 上**不可恢复**。
用户原话是「下一个版本开始」，边界非常明确，我不该追溯到历史。

### 原生菜单的限制

- **不给用 `enabled=false` 显示状态** —— Windows 会把整行变灰，连右边的数值一起灰掉。
  要显示不可选状态，做成**可点但空操作**。
- **emoji / 位图都不生效**，给不了菜单文字颜色。要颜色只能用系统自带的勾选态
  （`checked=true`，显示为蓝色勾）。
- **不做「点击才展开的独立菜单」** —— 展开时主菜单会消失、新菜单另起一处。
  在 Windows 原生菜单里，「贴合展开」与「悬停即展开」是同一套机制，拆不开。

### 改完的代码被 checkout 冲掉 —— 于是发了个「空包」

**症状**：用户报「点了关于没声音」→ 我改 `tray.cpp` → 报告已修复 →
用户试了说「没修好」。

**根因不在代码，在流程**：

```
① 改了 src/ui/tray.cpp（KillTimer 挪到回调之后）
② 为了换一种测试方法，执行 git checkout src/ui/tray.cpp   ← 修复被还原
③ 没有复核，直接提交
④ 提交信息写着「把 KillTimer 挪到回调之后」
⑤ git show --stat 只列了 3 个文件 —— 没有 tray.cpp      ← 铁证
⑥ 编译通过、冒烟通过、发版
⑦ 用户验证：没修好
```

**为什么特别危险**：这个错误**能一路通过所有检查**。
编译不会报错（代码本来就编译得过）、冒烟不会有异常（程序运行正常）、
发版流程完全顺畅 —— **因为「没改」和「改对了」在编译层面长得一模一样**。

**它违反的正是我自己写在禁止事项里的那条**：
「Edit / 脚本改完，立刻 grep 复核那一行」—— 我写了规矩，然后违反了它。

**预防**：

1. **改完立刻 grep 那行**（原规矩）
2. **提交后 `git show --stat` 核对**：提交信息提到的文件，在 `--stat` 里必须有
3. **大改动前先 commit**：这样 `git checkout` 只能还原「未提交的改动」，
   而不是把我的修复一起带走（我当时是先 checkout 再改的，顺序反了）

**这次修好之后的做法**：加了真走 `showMenu` 全程的测试入口，
用「弹窗期间心跳跳了几次」做判据 ——

```
修复前： 回调开始 ticks=86  → 结束 ticks=86   期间心跳 = 0     ✗
修复后： 回调开始 ticks=85  → 结束 ticks=244  期间心跳 = 159   ✓
```

**端到端的意思就是：真的走一遍用户走的路，而不是"代码里包了函数"。**

### 无人值守场景不许创建可见 UI

**症状**：开机自启后弹出一个黑色 cmd 窗口，关不掉也等不到；
**把它关掉，程序自己就退了。**

**根因**：

```cpp
bool hasArgs = argc > 1;               // ← 判据是「有没有参数」
if (hasArgs) {
    hasConsole = AttachConsole(ATTACH_PARENT_PROCESS) != 0;
    if (!hasConsole) hasConsole = AllocConsole() != 0;   // ← 凭空开窗
}
```

自启注册的命令是 `AirPlayBridge.exe --last` —— **`--last` 也是参数**。
而自启时没有父终端 → `AttachConsole` 失败 → `AllocConsole()` 新建控制台窗口。
**那个窗口就是进程自己的控制台，关掉它等于结束进程。**

同一段逻辑还影响：安装程序调用 `--fix-firewall --quiet`、卸载时的
`--uninstall-cleanup` —— **每次开机、每次装/卸，都会凭空多一个黑框。**

**判据错在哪**：「有参数」把两种完全相反的场景混为一谈 ——

  - 用户在终端里跑 `--list` / `--console` → **有人看** → 接上终端（有就复用，没有才新开）
  - 开机自启 `--last` → **没人看** → **绝不创建窗口**，输出走日志文件
  - 安装程序 `--fix-firewall --quiet` → **没人看** → 同上
  - 卸载清理 `--uninstall-cleanup` → **没人看** → 同上

**修法**：`AllocConsole` 只在**用户显式要求**时用（`--console`）；
其余一律「有终端就复用、没有就算了」。

**为什么这个 bug 只在自启时暴露**：从终端手动运行同一份代码，
`AttachConsole` 会成功，根本不走到 `AllocConsole` ——
**开发者天天从终端跑，永远看不到它。**

**通用教训**：

> **无人值守的启动路径（自启 / 安装 / 卸载 / 计划任务 / 服务）
> 不许创建任何需要人去关的东西。**
> 判断「要不要弹 UI、要不要开窗口」时，判据必须是
> **「这次启动有没有人在看」**，而不是「有没有参数」。

### 同一段 markdown，在不同位置渲染规则可能不同

发布正文是从 `CHANGELOG.md` 直接提取的，而 CHANGELOG 按 ~80 列手动折行
（便于阅读与 diff）。但 GitHub 对**位置**是分开处理的：

| 位置 | 单个换行 |
|---|---|
| 仓库里的 `.md` 文件 | 合并成空格 —— 看起来正常 |
| **release 正文 / issue 评论** | **就是硬换行** |

**同一份文字，在仓库里正常，在 release 页面里每个折行都成了真换行。**

修法不是在 CHANGELOG 里取消折行（那会毁掉 diff 的可读性），而是在**生成正文那一步**
把续行接回去。接缝处只在两侧都是可打印 ASCII 时才补空格（**中文之间不能有空格**）。

**判据**：凡是「把 A 处的文本搬到 B 处当正文」的地方，先问一句：
**B 处对换行 / 缩进的解释和 A 处一样吗？**

### 文档里的硬数字会腐烂

`AGENTS.md` 曾写着「有 19 条是踩过坑换来的」「硬约束 C1–C10」，
而实际的「禁止事项」已经有 **32 条**、硬约束到了 **C13**；
`ARCHITECTURE.md` 写 `main()`「约 960 行」，实际**近 1500 行**。

**这些数字没有任何自动化检查盯着 —— 只会越错越远。**

**规矩**：
- 能不给数字就不给（「每一条都是踩过坑换来的」比「有 19 条」耐放）
- 必须给范围时给**编号区间**（`C1–C13`）—— 它只在加条目时变，边界清楚
- **给清单加了项之后，顺手 grep 一遍引用它的地方，看数字还对不对**

**触发点**：每次给 `RULES.md` 加一条约束、给任何一个清单加一项，就是该扫这些数字的时候。

---

**这条后来做成了机器检查**（[RULES.md](RULES.md) **C14**）：

- 能机械核对的声明（档位表、滑块范围、约束编号区间、补丁文件数……）
  钉进 `tools/check_docs.py`，**CI 每次 push 都跑，`release.yml` 打包前也跑**
- **找不到声明锚点会 FAIL，不是静默跳过** —— 否则「把声明删掉」
  就成了悄悄关掉检查的手段
- 判断类的（措辞、完整性）走 C14 的**窄触发表**：改了才查，不是每次查

**为什么不做「每次改完全面排查文档」**：那种规则触发条件太宽，
大部分时候没事可做 → 变成噪声 → 被跳过 → 跳过第一次就没有第二次。

### 交接给别人的东西，不许写绝对路径

**事故（2026-10-24）**：连着写了五份整改报告，每次在对话里回报位置都写成

```
C:\Users\Administrator\Desktop\AirPlay-Bridge-审查报告\27-整改-….md
```

被用户当面退回：**「不要给绝对路径啊，给相对路径，不让别人读不到啊」**。

**为什么绝对路径是错的**：

- 换一台机器就不存在 —— 路径里的用户名、盘符、目录结构全是**别人环境里没有的**
- 发给别人等于发了一个**读不到的位置**，比不给还糟：他以为有东西可以去拿
- 写进文档后还会**慢慢腐烂**（同上一节「硬数字会腐烂」）：
  目录一改名，全文所有引用同时失效，而且没人会回来改

**规矩**：

| 场合 | 写法 |
|---|---|
| 同一目录下的另一份报告 | `[24-整改-….md](24-整改-….md)` —— 纯文件名 |
| 仓库里的文件 | 相对路径 `docs/PITFALLS.md`、`src/app/airplay_bridge.cpp` |
| 仓库外的文件 | 说明「在哪、叫什么」，不给绝对路径 |
| 真要给绝对路径 | 只在对**本机同一个人**的即时回复里，并说明是"你自己机器上的" |

**交叉引用还有一条**：写「详见 23 号报告第五节第五节」这种**既含糊又打错**的
引用，等于没引 —— 读者不知道 23 号是哪份、第五节在哪。
要么写全文件名做成链接，要么别引。

**判断标准**：**对方拿到这段文字，能不能直接找到东西？** 拿不到就是没写对。
**窄触发 + 机械检查**才活得下来。

## ⑥ 发布纪律

### 文档改动不升版

升版 = **给用户一个新的安装包**。exe 和上一版一模一样时，**那个版本号是假的** ——
用户装完发现「跟上次没区别」，第一反应是「是不是没更新成功」，然后来找你。

**事故**：README 补了界面语言的说明，我照惯例升版发了 v1.4.7，
而 exe 一个字节都没变。用户一句话点破：**「代码没动 为啥升版呢？不是跟上版一致吗？」**
已撤回 release / tag / CHANGELOG 条目，版本号退回。

**判据**：这次改了 `src/` 下的代码吗？

**更普适的一条**：既有的发版检查清单（编译 / 冒烟 / 版本号 / 核对二进制 / 更新桌面）
全都在回答「这个版本**好不好**」，**没有一项回答「该不该存在」**。
发版是一个**给用户新东西**的动作，不是流程的终点。

### 改了代码却没发版 —— 这条的反面（2026-10-23）

上面那条讲「**不该发**的时候别发」，漏了反面：**该发的时候要发**。
两边是同一个判断，只写一边就会走偏 —— 我照着「文档不升版」的纪律，
把代码改动也一起留在了 main 上。

**事故**：托盘提示改成多行（`src/` 下的代码），推到 `main` 就报告「已推送」，
但**没打 tag**。`release.yml` 只在 `git push origin vX.Y.Z` 时才构建，
于是线上 Release 停在旧版 1.5.32，用户装了最新包，看到的还是旧行为 ——
「你根本没改啊」。用户的判断没错，**是我把「推送」当成了「发版」**。

**判据（和上一条配成一对）**：

| 这次改了什么 | 动作 |
|---|---|
| 只有 `docs/` `README` `.github/` | 推 main 即结束，**不升版不打 tag** |
| `src/` 下任何会进 exe 的东西 | 推 main **之后必须**升版 + 打 tag |
| 两者都有 | 按「有代码」处理 —— 发版 |

**「推送成功」不是交付完成的信号。** 交付的终点是
`releases/latest` 上的 tag 变了、安装包换名了。在那之前，
用户手里跑的还是旧代码，说得再多都没用。

**自查一句话**：改完之后问「用户下次装的时候，会拿到这次的东西吗？」
答不上来就是没发。

### 验证前先核对被测二进制的版本号

两次报「验证通过」，实际测的都是**旧版**的行为：

- 第一次：安装被 `UsePreviousAppDir` 带到了之前的临时目录，
  `Program Files` 根本没被碰，我却在那个旧 exe 上测「启动静默」✓
- 第二次：同样的形式，装完显示 1.2.53，我竟然没停下来问为什么

**版本不对，后面所有「通过」都是假的。** 这比「跑一遍路径」更前置 ——
你连跑的东西是不是新的都不知道。

### 发版前扫一眼「最近交代过什么」

指示落在对话里、不落到行动上就等于没听见。
我曾被告知「下个版本起只发安装版」，40 分钟后发版时完全没想起来，
还手动把便携版 cp 到了桌面。

### 只在 CI 上编译的东西，改之前先查文档（2026-10-24）

**本地跑不了的东西，改它就没有"改错了会立刻知道"这回事 —— 唯一的反馈是 CI 挂掉，
而那时 tag 已经推上去、release 已经开始了。**

**事故**：给安装器加"跟随系统语言"的开关，凭记忆写成

```ini
LanguagesDetection=auto          ; ← 这个指令不存在
```

Inno 不认，报「未知指令」当场中止打包。`build` job 挂在「打包安装程序」，
`publish` job 被 skip —— **tag 推出去了，安装包没出来**。

正确写法是 `LanguageDetectionMethod=uilanguage`（合法值只有
`uilanguage / locale / none`，而且 `uilanguage` 本来就是默认值）。

#### 为什么偏偏栽在这一类文件上

| 文件 | 本地能验证吗 |
|---|---|
| `src/**` C++ | ✅ 能，`cmake --build` 秒报 |
| `tools/check_docs.py` | ✅ 能，直接跑 |
| `README` 数字 | ✅ 能，跑门禁 |
| **`installer/*.iss`** | ❌ **CI 才有 Inno Setup** |
| **`.github/workflows/*.yml`** | ❌ **只有 GitHub 认** |

前四类的错误会被本地的编译/门禁拦下，我形成了"改完立刻知道对不对"的习惯；
后两类**没有这一层**，习惯却照搬过来，就成了凭记忆裸奔。

#### 所以

1. **改 `.iss` / workflow 前，先查官方文档确认字段名**（`jrsoftware.org/ishelp`、
   GitHub Actions 文档）。两分钟的事，比一次失败的 release 便宜得多
2. **推 tag 前想一遍：这次改的文件，本地验证过吗？**
   没验证过的，先用 `workflow_dispatch` 手动跑一次打包产物 ——
   `release.yml` 支持手动触发且**只出产物不建 release**，就是为这个留的
3. **tag 不是不可撤回的**：发错了 `git push origin :refs/tags/vX.Y.Z` 删掉、
   修好重打即可。但**别把它当常规操作** —— 已经有人下载过坏包就等于发出去了

> 同类问题的普适形式：**"我的验证手段覆盖不到我这次的改动"**。
> 感觉"改完就行"的时候，先问一句「我改的东西，本地跑得起来吗？」


## ⑦ 算法与数值

### 分块不变性（2026-10-17，外部审查发现）

**这是本项目第一个由外部代码审查发现、而不是自己踩出来的 bug。**
也正因为如此，它暴露了我排查方法上的一个盲区。

#### 现象

同一条输入流，仅改变喂入的分块大小，重采样器的输出就不同：

```
修复前，48k->44.1k，品质 100，同一条 1kHz 正弦：
  分块   1     最大样点差 52386    输出帧数 48000（应为 44070）
  分块   2     最大样点差 53904
  分块   7     最大样点差 54024
  分块  64     最大样点差   574
  分块 480     最大样点差  3582     <- 线上回调常见的块大小
  分块 882     最大样点差 21002
  分块1024     最大样点差 20541
  分块4096     最大样点差   552
```

**64 帧和 4096 帧几乎不出错，480 帧差 3582，1 帧差 52386 —— 毫无规律。**

听感上是高频失真和电平起伏，与实际用哪个分块有关。

#### 根因：两层

**第一层（审查者指出的）：历史缓冲长度塌缩。**

```cpp
const size_t keep = histLen;                  // 进入本次调用时的长度
const size_t cnt  = min(keep, total - from);  // 可用部分不够时被夹小
histL_ = tailL;                               // 长度永久变小
```

可用的尾部少于 `keep` 时历史被夹短，下次 `keep` 更小，持续塌缩。

**第二层（实测才发现的，更根本）：结构上就不是分块等价的。**

```cpp
if (center + 1 >= total) break;               // 只检查前向边界
for (int k = -half; k <= half; ++k) {
    if (idx < 0 || idx >= total) continue;    // 左侧不足就跳过抽头
```

sinc 插值需要 `center ± half`（±33）个真实样点。左侧不足时抽头被跳过，
归一化后的幅度和相位都是错的。而「左侧不足」出现的频率随分块变化 ——
**所以改历史长度解决不了它。**

#### 修法：重写核心循环

把「滑窗 + 每次重算」换成「连续输入历史 + 绝对读取位置」：

```
维护:
  histL_      从 histBaseAbs_ 这个绝对位置开始的输入片段
  posAbs_     下一个输出样点在输入时间轴上的绝对位置

产出前先判断左右邻是否都齐:
  if (leftNeed  <  histBaseAbs_) break;   // 左邻不够 -> 等
  if (rightNeed >  availEnd)     break;   // 右邻不够 -> 等
```

`reset()` 预填 `half` 个零代表「信号开始之前的静音」，第一个样点就有完整左邻。

**修复后：8 种分块大小全部 0 差异**；同时 19.9kHz 信噪比从 39.5dB 提到 41.7dB。

#### 三次失败的修法（都是"打补丁"）

| 尝试 | 结果 |
|---|---|
| 只改保留长度为 `taps_` | **更差**（52529）—— `pos_` 基准没跟着改，时间轴错位 |
| 改长度 + `pos_` 减 `newOrigin` | 480 帧对了（73），其他分块仍错 |
| **重写核心循环** | ✓ 全部分块 0 差异 |

**教训：结构性问题不能靠调参数解决。** 前两次都能自圆其说（"长度对了应该就行"），
但一测就露馅。

#### 还有一个自己引入的 bug（修的过程中）

`configure()` 里 `reset()` 排在 `taps_` 计算**之前**，导致预填长度按 `half=0` 算；
`taps_` 变大后左侧永远不够 → **一个样点都产不出**。
在 `configure()` 末尾补第二次 `reset()` 修好。

#### ★ 为什么之前的排查没发现（这条最值钱）

我做过一轮"十类全面排查"：越界写、线程竞态、内存安全、资源释放、并发、
输入边界、发送链路…… **十类里没有一类是「把核心算法单独拎出来做数值验证」。**

那一轮排查的方式是**读代码 + 静态分析**。而这个问题：
- 读代码看不出（每一行都"合理"）
- 编译不报错
- 冒烟测试正常（程序能连上、能出声）
- **原有测试也测不出来** —— 因为它只喂一次大缓冲，正好落在"几乎没事"的 4096 帧那一类

**唯一能抓到它的方式是：同一条输入，换个分块大小，比对输出。**

**规矩**：有内部状态的数值算法（重采样、滤波、混响、编码器），
**必须有「不变性测试」** —— 找到一个"换个用法就应该完全一样"的量，
然后真的去比。这类不变量包括：
- 分块不变性（流式 DSP）
- 精度不变性（float vs double 的差异应在预期内）
- 顺序不变性（先 A 后 B vs 先 B 后 A，若可交换）

#### 外部审查的价值

这份报告的价值不在于"找出了一个 bug"，而在于它做了我没有做的动作：
**把算法移植出来，实际跑一遍。**

它自己是诚实的 —— 附录里写明"本机无 MSVC，无法编译原程序验证，建议在真实构建环境复核"。
我照做了，用真实 MSVC 编译，结果比它的 Python 移植**更严重**
（1 帧分块时连输出帧数都不对，它没测到这个）。

**教训**：读代码能理解"逻辑"，但**数值正确性必须跑**。
而我过去倾向于"读懂就算排查过了" —— 那是把阅读理解当成了验证。

## ⑧ 修完怎么自查

**这一节不是"某个 bug 的原因"，是一套自查动作。**
适用于任何"我改了一段控制流"的场合。

**四条**（前三条管"会不会执行"，第四条管"量到的对不对"）：

| # | 问什么 | 防的是 |
|---|---|---|
| 一 | 新加的守卫条件，在你要保护的场景里取值是什么 | 条件恒假 |
| 二 | 删掉的那行，原来在哪些路径上生效 | 移动后覆盖不到 |
| 三 | 注释逐字对得上代码吗 | 承诺失真 |
| 四 | **你读的那个量，是什么时候开始攒的** | 数据里混着不该有的东西 |

起因是 2026-10-24 那双复查：两处修复**编译过了、单元测试过了、门禁过了，
但运行时永远走不到那段代码**。12 项一次通过，只有这 2 项翻车，
翻车方式完全相同 —— 这不像偶然，像方法缺失。

**后来又被打回一次**，第四次才改对：那次代码是**会执行**的，
但判据读的峰值统计从连接握手**之前**就开始攒，
窗口里混着静音前的响亮音频 —— 这就是第四条要防的东西。
所以下面第 1–3 条只覆盖了"能不能跑到"，第 4 条覆盖"跑对了没有"。

### 一、新加的守卫条件，在你要保护的场景里取值是什么

**事故（P1-4）**：给「静音掐断采集」加防护，条件是

```cpp
if (... && !standbyActiveConfig(cfg)) {   // 待机关着才检查
```

而这个 bug 的断连循环，**"拆会话"那一步就是待机机制本身** ——
循环只在**待机开着**时存在。待机默认开着（`standbyEnabled = true`、5 秒），
于是 `!standbyActiveConfig(cfg)` 在默认配置下**恒为假**，
这段防护一次都没执行过。

更讽刺的是：我用「待机」当防误伤的条件，可检查只在待机关闭时才跑 ——
**防误伤的判据与检查生效的条件恰好互斥，等于把自己堵死了。**

反过来还有第二层：就算去掉这个条件也攒不齐。撤销判据要连续 6 个 5 秒窗口，
而 5 秒待机就把 `running` 打成 false、计数器每轮清零 —— **30 秒永远到不了**。

**做法**：写完一个守卫，把它代入"我声称它要保护的那个场景"，
逐个条件求值，看整体是不是 `true`。**默认配置尤其要代一遍** ——
默认值往往正好是最常见的场景，也是我测试时最容易跳过的场景
（我自己的机器改过配置）。

### 二、删掉的那行，原来在哪些路径上生效

**事故（P2-1）**：把「重连退避翻倍」从掉线支提到块入口，条件里带了

```cpp
if (sess.running.load() && sess.wantReconnect.load() && everConnected && ...)
```

而掉线支的进入条件是 `!sess.running.load()` —— **在那里恒为假**。
等于把掉线支原有的翻倍删掉了。后果：设备掉线后永远卡在 10 秒重试。

**做法**：移动一段逻辑时，先列全**它原来服务的所有入口**，
再逐个确认新位置覆盖得到。数量对不上就说明漏了。

### 三、注释是承诺，不是解释

上面那条我在掉线支删了翻倍后写：

```
// 退避翻倍已提到上面 retry 判据那里统一处理 ——
// 两支共用，避免只有「掉线」加速、「被踢」不加速。
```

**"两支共用"与代码事实相反。** 复查方两次都用"注释声称与代码事实不符"
来定性，措辞比功能回归还重 —— 原因很实在：

**错误的注释比没有注释更坏。** 没有注释，下一个读代码的人会自己去读逻辑、
自己发现问题；有了一句自信的错误注释，他会信，然后跳过验证。

**做法**：注释里凡是出现"统一处理""共用""都走这里""已经覆盖"这类
**全称判断**的，写完立刻回头核一遍代码 ——
全称判断最容易错，也最容易骗过明天的自己。

#### 尤其是"排除性断言"，要代「功能正常工作时的状态」

**事故（2026-10-24，诊断日志刷屏）**：给一条诊断日志写注释：

```
// 这条日志只在与静音相关时写，正常播放不会走这里（外层要求 g_mutedByUs）。
```

**这句是错的。** `g_mutedByUs` 恰恰在这个功能**正常工作**期间恒为真，
而"撤销永不发生"是健康机器的常态 —— 也就是说，
**这个功能的正常状态，正好命中了我以为的异常分支**。

后果：健康驱动 + 默认配置的用户，每次暂停后唤醒，
之后每个有声音的 5 秒窗口都记一条，一小时约 720 条。

**做法**：写"不会走这里""只在这种情况下发生"这类**排除性断言**时，
把断言代入**两个**状态各跑一遍：

| 代入 | 结果 |
|---|---|
| 异常状态（真出问题时） | ✅ 会走 —— 我以为的 |
| **正常状态（功能正常工作时）** | ❌ **也会走 —— 漏的** |

这次一代入立刻露馅：功能正常时 `g_mutedByUs` 为真、
`fromWake` 为真、`pk` 有电平，三个条件全满足。

**只代异常状态，就会写出"只有出错时才走这里"这种一厢情愿的注释。**

#### 同一个病灶，四次换皮

| 次 | 形态 |
|---|---|
| 1 | `muteGaveUp` 文档承诺：写「手动开关仍生效」，只兑现"关"方向 |
| 2 | `muteCheckFromWake`：只在成功路径消费，失败路径不清 |
| 3 | 诊断日志：写「正常播放不会走这里」，正常状态恰恰会走 |
| 4 | 注释残骸：同一块里前半句"记完清 `muteFromWake`"、后半句"**不能清**" |

四次都发生在**我刚写完相关教训之后**。

这说明：**写下教训 ≠ 免疫。** 那段「注释是承诺」我写得越顺，
越容易在下一次想都不想就写下一句自信的断言。

所以上面那两条"做法"不是知识，是**动作** —— 必须当场做，不能只记住。

### 四、你读的那个量，是什么时候开始攒的

**这一条比前三条深一层。** 前三条约等于问"这段代码会不会执行"，
这条问的是"**它量到的东西对不对**" —— 代码执行了、条件也满足了，
但读到的数据里混着不该有的东西。

**事故（P1-4 的第三次返工，2026-10-24）**：

判据要回答"静音之后还有没有电平"，做法是每 5 秒读一次峰值统计
`g_peakWindowMax`，连续为 0 就撤销静音。

统计看着没问题，问题在**它从什么时候开始攒**：

```
start():  开采集(:2186) → 起 producer(:2352) → 握手(:2419)
```

采集和累积**都早于握手**，而静音发生在 `launched(true)` 里 —— 即握手**之后**。
于是静音那一刻，统计里已经存着握手期间（0.5~2 秒）的**静音前响亮音频**。

后果是可以算出来的：静音发生在 `h`，连接后第一个检查点在 `(h, h+5]`，
它的统计窗口**必然**覆盖 `(h-5, h)` 那段静音前的响亮帧 → 读到高电平 →
计数器清零。而默认待机也是 **5 秒**，第二个干净窗口最早 `h+10`，
待机在 `h+5` 就拆会话了。

**窗口长度 == 待机时长，所以是确定性失效，不是偶发。**

修法一行：

```cpp
// setSystemMuted(true) 之后
g_peakWindowMax.store(0);   // 窗口锚定到静音时刻，只量静音后的电平
```

**问法**（对每一处"读某个累积量/计数器/标志"的判据）：

1. **这个量是什么时候开始攒的？** 从进程启动？从会话建立？从那次事件？
2. **我这次要排除的东西，会不会已经在里面了？**（静音前的音频、上一个会话的残留）
3. **判据生效的时刻，和事件发生的时刻，谁先谁后？** 算一遍具体数字 ——
   这次就是 `窗口 5s == 待机 5s`，一算就露馅，前三轮都没算。
4. **这中间隔着多久？** 握手要 0.5~2 秒，这段时间的量算不算数？

**这类错误编译、单元测试、文档门禁三者都天然看不见** ——
它们都不模拟"时间"。能抓住它的只有两种东西：
**人把时序写下来算一遍**，或者**一个现场日志**。

所以判据涉及时序时，**顺手加一条观测日志**（判据被触发/被重置时记下读到的值）。
下次用户报"还是不对"，日志能直接分辨是"判据被污染"还是"这个场景根本不适用" ——
而不必再猜一轮。这一条在第四次返工后补上了。

### 一个共同点

四件事都落在同一个缝里 —— **"代码写出来了"与"代码会做对事"之间**：

| | 写出来了 | 会执行吗 | 量到的对吗 |
|---|---|---|---|
| P1-4（第一版） | ✅ 逻辑正确 | ❌ 默认配置下条件恒假 | — |
| P2-1 | ✅ 翻倍逻辑正确 | ❌ 掉线支条件恒假 | — |
| 注释 | ✅ 语句通顺 | ❌ 描述的行为不存在 | — |
| P1-4（第三版） | ✅ 会执行、也能攒 | ✅ | ❌ 窗口里是静音前的音频 |

**层层往下，工具能帮的忙越来越少：**

| 层 | 问题形态 | 谁能发现 |
|---|---|---|
| 1. 语法 / 类型 | 编译不过 | 编译器 |
| 2. 逻辑算错 | 函数返回错值 | 单元测试 |
| 3. **控制流不可达** | 条件恒假、分支进不去 | 只有人：代入场景求值 |
| 4. **数据时序不对** | 会执行，但量到的东西不是要量的 | 只有人 + 现场日志 |

`P1-4` 修了四轮，正好走完第 3 层到第 4 层：前两次死在第 3 层，
第三次会执行了、卡在第 4 层。**每往下走一层，就越不能指望工具。**

所以改完控制流，问的不是"编译过了吗"，而是三句：

> **这段什么时候会被执行到？**（第 3 层）
> **它读的那个量，是什么时候开始攒的？**（第 4 层）
> **我写的注释，逐字对得上代码吗？**（承诺）

三句都答得上来，才算改对。
